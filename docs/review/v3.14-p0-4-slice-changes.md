## 一、问题 / 背景

旧 stdin 主循环对每个 GUI 方法 `threading.Thread(target=worker, daemon=True).start()`（原 2404-2411），
多个 UIA 自动化动作可并发交错抢同花顺唯一窗口；且 `gui_lock`（原 806）只在抢锁（30s 超时）层面互斥，
**拿到锁之后的操作体没有硬超时**，GUI 卡死会让作业无限悬挂、槽位永不释放。

本切片只交付「可纯测、可验证」的部分：
1. 纯组件：有界串行 `OperationQueue`（10s 硬截止 fail-safe，超时只发 error、绝不发 cancelled/filled）、
   `BackoffReconnectPolicy`（退避序列 + 成功重置）、`ActivityMonitor`（活性/停滞看门狗）；
2. 薄接线：stdin 的 GUI 方法改走队列串行，`confirm/reject/captcha_input/heartbeat` 保持即时不排队；
3. 不可真机验证的进程重建 / 深度线程复位明确延后，不硬写。

### 1.4 硬截止预算分类（复核修正增补：避免把合法人工等待误判为假失败）

问题：原 `sweep_timeouts` 到 10s 即把所有 running 作业判 `timeout_failed` 并发 error，
会把仍在进行的**半自动人工确认等待（≤300s）**与**验证码人工输入等待（≤120s）**误判为超时假失败。

修正（最小、可纯测，不硬写线程强杀）：

- `OperationJob` 新增 `timeout_budget`（`sidecar_client.py` 767-780）：有限秒数=仅清扫过期；
  `None`=交互作业，sweep 跳过、永不判 `timeout_failed`。
- `enqueue(..., timeout_budget=10.0)`（809）：省略=有限 10s；显式 `None`=交互豁免。
- `sweep_timeouts`（871）：仅当 `budget is not None and budget >= 0 and now-started_at >= budget`
  才判 `timeout_failed`；交互作业（None）直接跳过。
- main() 接线新增 `_budget_for(method)`（2615 附近）分类：
  - `submit` / `position_order` 且 `auto_confirm=False` → `None`（半自动人工确认等待，交互豁免）；
  - `query_position` / `query_trades` / `query_pending` / `cancel` → `180.0`（读表/撤单读回可能触发
    验证码人工输入 ≤120s，给宽裕有限预算；真挂死仍终会失败，不无限豁免）；
  - 其余（query_asset / send_key / click / check_app / current_page）→ `10.0` 纯自动化 fail-safe；
  - `auto_confirm=True` 的 submit/position_order 仍走 10s fail-safe。
- 派发处 `opq.enqueue(method, p, cid, timeout_budget=_budget_for(method))`（2656 附近）。

边界与残余限制：10s 硬截止只作用于纯自动化 UIA 段；人工确认/验证码等待豁免，绝不被 10s 杀掉。
交互作业在串行 worker 内阻塞期间占用队列（单操作员串行语义），「挂死中继续派发」属深度线程复位，延后。

- 复核修正新增（`P04OperationQueueTest`）：
  - `test_interactive_job_exempt_never_times_out`：budget=None 交互作业时钟推进到 999s 仍保持 running、
    不发 error、不进 completed、active 不释放；
  - `test_generous_budget_not_false_failed_at_10s`：180s 宽裕预算作业在 10s 不被误判 timeout_failed。
  - 既有 `test_timeout_marks_failed_only_error_...` 仍验证有限预算 10s 超时只出 error、绝无 cancelled/filled。

## 四、延后项（本切片不实现，需真机验证）

1. **xiadan.exe 进程探测 / 自动重启 / 断连重建循环**：`connect()`（真实模式 1427 起）现为一次性、无重建；
   自动重启与断连重建需真机拔线/杀进程验证，本切片只交付就绪的纯组件与状态上报，不硬写重建。
2. **重建后轮询恢复（重新 find_main_window / 重连 / 补对账）**：依赖重建循环，一并延后。
3. **深度线程复位**：Python 无法强杀阻塞线程；live 下真正「线程级打断、复位悬挂线程、让队列在挂死中继续」
   需真机注入卡滞验证，本切片不硬写。队列层 fail-safe 只负责状态记账、释放 FIFO 槽位与上报 error，
   阻塞线程由其自然返回。
4. **心跳活体联动**：`heartbeat_loop`（306-309）仍为盲发，Rust 暂无断线分支；本切片未接入，延后。

## 五、已知限制

- live 半自动/验证码：人工确认等待（`slot.event.wait` 最长 300s）与验证码等待（约 120s）发生在作业内部，
  **豁免 10s 硬超时**，绝不能被 fail-safe 杀掉；当前串行 worker 在该等待期间占用队列（单操作员串行语义可接受），
  「挂死中继续派发」属深度线程复位，延后。
- 10s 硬超时只作用于 UIA 自动化段（拿锁 + 自动动作），不适用于人工确认 / 验证码等待 / HTTP 同步终态等待。
- `ActivityMonitor`/`BackoffReconnectPolicy` 本切片仅交付纯状态机并在接线处记账，未接真实重启动作。
- 纯测用注入时钟驱动超时，不依赖真实线程时序；真实线程级 10s 自愈需真机注入卡滞验证（见延后项）。
